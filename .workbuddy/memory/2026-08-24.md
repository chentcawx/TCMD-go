## Bug 修复：含破折号"——"文件名显示错位（09:26–09:35）
- 现象（用户）：处理文件名含"——"（em dash U+2014）时造成显示错误。
- 第一性原理追踪：
  1. 宽度算法不统一：bubbletea/lipgloss 实际渲染用 `lipgloss.Width`，而 `truncateDW`/`padRightDW`/`padLeftDW` 之前用 `runewidth.RuneWidth`/`runewidth.StringWidth`。
  2. 两把尺子对**模糊宽度字符**判定冲突：本机实测 `runewidth.RuneWidth('—')=2` 但 `lipgloss.Width('—')=1`；`runewidth.RuneWidth('│')=2` 但 `lipgloss.Width("│")=1`。
  3. 后果：`truncateDW` 按 runewidth 把"——"当 4 格预算，但终端 lipgloss 实际只画 2 格 → 含 em dash 的文件名行在 lipgloss 视角比预算窄 2 格 → size 列向左偏移 2 格、与同行其他列不对齐（显示错误）。
  4. 更隐蔽：分隔符"│"在 lipgloss 下占 1 格，但 `View()` 的 `sepW` 用 `runewidth.RuneWidth('│')=2` 扣宽度，导致右面板少算 1 格（与 ConPTY 宽度偏差叠加偶发溢出）。
- 修复（统一为 lipgloss.Width 单一权威尺子）：
  - `truncateDW`：单字符宽度预算从 `runewidth.RuneWidth(r)` 改为 `lipgloss.Width(s[i:i+size])`（与终端实际绘制一致）。
  - `padRightDW`/`padLeftDW`：`runewidth.StringWidth` → `lipgloss.Width`。
  - `View()` 的 `sepW`：`runewidth.RuneWidth('│')` → `lipgloss.Width("│")`（=1，与真实渲染一致）。
  - `mouse.go` 的 `sepCol()` 硬编码 `sepW:=2` → `lipgloss.Width("│")`；`runeWidthOf`/`contextMenuWidth` 的 `runewidth.StringWidth` → `lipgloss.Width`。
  - 测试：`layout_test.go`/`layout_tab_test.go` 内宽度断言从 `runewidth.StringWidth`/`runewidth.RuneWidth` 全面改为 `lipgloss.Width`，`sepW` 同步；删除 runewidth import（view.go/mouse.go/layout_test.go/layout_tab_test.go）。
  - 新增 `TestAmbiguousWidthAlignsColumns`（含 em dash 的 formatEntry 行 lipgloss 宽度必须 == 纯 ASCII 行，锁死列对齐）+ `TestTruncateDWUsesLipglossWidth`（truncateDW 对"——"按 lipgloss 2 格预算）。
- 验证：go vet 干净；go test ./... 全绿；临时诊断确认所有含"│"行 lipgloss 宽度恒等于终端宽（无溢出/无短缺）。
- 构建：dist/tcmd64.exe(5.31MB) / dist/tcmd386.exe(5.00MB) 双架构重建。
- Release: v0.4.3。
- ⚠️ **v0.4.3 的尺子方向选错（见 v0.4.4）**：lipgloss 对 ambiguous 字符按 1 算，比多数终端实际（2）更激进，在"终端把 em dash 画 2 格"的 CJK 环境会**溢出**。

## Bug 修复：含"——"文件名下方多出一行（09:44–09:51）
- 现象（用户，v0.4.3 后新现）：含"——"的文件名下方多出一行 `R>2 <DIR>`（目录项被挤到"多出来"的行）。
- 根因（第一性原理）：`—`(U+2014) 是 East Asian Ambiguous 宽度字符，实际终端宽度取决于终端 locale。
  - 本机 lipgloss 判定 em dash=1（与本机终端一致，故本机不溢出、无法复现）。
  - 但用户的 Windows Terminal（CJK 环境）实际把 em dash 画成 **2 格**。
  - v0.4.3 统一成 lipgloss（em dash=1 预算）→ 用户终端画 2 → 每行比预算多 1 格 → 超宽 → 终端把超宽部分 **wrap 到下一行** → 即"多出来的一行"。
  - 反证：v0.4.2 之前 truncateDW/pad 用 runewidth（em dash=2 预算），终端画 2 → 行宽恰好 = 终端宽 → 不溢出（那时只因 clampRowWidth 用 lipgloss 导致列对齐错，未溢出）。
- 修复（统一回 runewidth 单一权威尺子，保守且永不溢出）：
  - `truncateDW` 预算：`lipgloss.Width` → `runewidth.RuneWidth(r)`。
  - `padRightDW`/`padLeftDW`：`lipgloss.Width` → `runewidth.StringWidth`。
  - `clampRowWidth`（v0.4.2 漏改处）：`lipgloss.Width` → `runewidth.StringWidth`（这是 v0.4.2 列对齐错的真正根源之一）。
  - `View()` `sepW` / `mouse.go` `sepCol()`：`lipgloss.Width("│")` → `runewidth.RuneWidth('│')`。
  - `runeWidthOf`/`contextMenuWidth`：`lipgloss.Width` → `runewidth.StringWidth`。
  - 恢复 view.go/mouse.go/测试文件的 runewidth import；测试断言统一改 runewidth。
  - 测试改名/改写：`TestTruncateDWUsesLipglossWidth` → `TestTruncateDWUsesRunewidthWidth`（断言 em dash 按 runewidth=2 预算）；`TestAmbiguousWidthAlignsColumns` 加 `runewidth 宽 ≤ w` 防溢出断言。
- 为什么 runewidth 统一比 lipgloss 统一稳：runewidth 对 ambiguous 字符默认=2，匹配 East-Asian 终端常见绘制；在"终端画 2"环境完美对齐不溢出，在"终端画 1"环境（本机）最坏仅右侧多留白、绝不溢出。lipgloss 统一则反之（本机完美、用户环境溢出）。
- 验证：go vet 干净；go test ./... 全绿；临时诊断确认所有行 lipgloss 宽 ≤ w（不 wrap），runewidth 宽 = w（列对齐）。
- 构建：dist/tcmd64.exe(5.31MB) / dist/tcmd386.exe(5.00MB) 双架构重建。
- Release: v0.4.4。
- **经验沉淀（修正 v0.4.3）**：TUI 列对齐/不溢出类 bug，**统一用 runewidth 作为唯一宽度尺子**（保守，匹配 CJK 终端），禁止混用 lipgloss.Width；ambiguous 宽度字符（em dash '—'、'│'、弯引号、全角破折号）是主要雷区，且不同终端实际宽度可能不同——保守尺子（=2）比激进尺子（=1）安全。

## 破折号 bug 真因定位 + 实证回归测试（22:16 起，跨会话续修）
- **用户纠正**：v0.4.2/v0.4.3/v0.4.4 的提交发布是"自以为修复"，未经用户真机验证，且 v0.4.4 在用户终端仍复现"含'——'文件名下方多出一行 '>'"。已按 skill 3.7 加 GitHub 同步门控（修复未验证生效前禁止 commit/push/tag/release）。
- **真正根因（v0.4.4 仍漏改处）**：`truncateDW` 顶部有一个 lipgloss 早期返回守卫 `if lipgloss.Width(s) <= max { return s }`。
  - 实测（go-runewidth v0.0.19）：`lipgloss.Width("——")=2`，但 `runewidth.StringWidth("——")=4`，终端（CJK）按 **4** 画。
  - 守卫用 lipgloss 尺子 → 含 em dash 的文件名在 lipgloss 视角"够窄"直接整串返回、**根本不进 runewidth 预算循环** → 行实际超宽 → 终端 wrap 到下一行（即"多出来的 > 行）。
  - v0.4.4 只把循环/pad/clamp 改回 runewidth，**没动这个 lipgloss 守卫**，所以没修好。
- **关键测量事实（已用探针实证，勿再假设）**：
  - `runewidth.StringWidth` 会把 ANSI 转义序列当可见字符算（"\x1b[44mabc\x1b[0m" 报 10，实际 3）→ **绝不能用它做带样式的整行宽度断言/预算**。
  - `lipgloss.Width` 是 ANSI-safe 的（同上例报 3），但对 ambiguous 字符按 1 算（em dash=1，终端画 2）→ 用作预算会**低估**溢出。
  - 结论：预算只能用 `truncateDW` 现有的"逐 rune + 跳过 ESC + `runewidth.RuneWidth`"循环（ANSI=0、em dash=2，唯一与终端一致）；lipgloss 仅适合做"无 ambiguous 字符风险"的断言。
- **修复**：删除 `truncateDW` 的 lipgloss 守卫（循环自身正确处理"够窄"情形），并修正文档注释（原注释误称"预算用 lipgloss.Width"）。
- **实证回归测试（关键纪律：先证伪再收工）**：
  - 新增 `TestTruncateDWGuardUsesRunewidthWidth`：用 `max=3` + `"——"`（lipgloss=2≤3 但真实=4>3）逼出守卫 bug。
  - 强化 `TestViewRowsStayWithinWidth`：断言 oracle 在 `lipgloss.Width` 之外，额外用 `runewidth.StringWidth(stripANSI(line))` 测"真实绘制宽度"，并在 fixture 加一条 em dash 长文件名。
  - **反向验证**：临时把 lipgloss 守卫塞回代码 → 两个测试**确实 FAIL**（`painted width 61 > 60` / `"——" width 4 want 2`）→ 还原后 PASS。证明测试非同义反复、真能拦住回归。
- **验证**：go vet 干净；`go test ./internal/tui/` 与 `./internal/fs` 全绿；双架构重建 dist/tcmd64.exe(5.57MB)/tcmd386.exe(5.24MB)。
- **未发布**：按 skill 3.7，未 commit/push/tag/release，待用户真机验证。v0.4.3/v0.4.4 的 GitHub Release 已是 Draft 状态（tag 已删），v0.4.2 仍 Latest（属另一 bug，与破折号无关）。

修复五项交互/快捷键缺陷：

### 1. 双击标签回退到根目录显示 "E:."
- **根因**：`filepath.Base("E:\\")` 在 Windows 返回 `"\\"` 而非 `"."`；`pathPrefixAtSegment("E:\\", 0)` 返回 `"E:"` 而非 `"E:\\"`，导致 handleDoubleClick 中 `target != path` 为 true，触发 newTabAt("E:", "\\")——"E:" 是无效路径。
- **修复**：`pathPrefixAtSegment` 对 Windows 根路径（segs==1）在返回时追加尾部 `\`，使 `"E:\\"` 成为有效目录路径；测试 pathseg_test.go 更新断言 `{C:\, 0, C:\}`。

### 2. 鼠标滚轮逐行滚动
- **根因**：handleMouse 的 WheelUp/WheelDown 调用 pageMove(±1)，pageMove 每次跳约半屏（10 行或 (height-6)/2）。
- **修复**：新增 `model.incrementRow(d int)` 方法（精确移动 1 行），handleMouse 改为调用 incrementRow(±1)。

### 3. Ctrl+2/3 排序热键失效
- **根因（经 bubbletea key_windows.go 源码验证）**：
  - Windows console 下 ctrl+a/b/c → `KeyCtrlA/B/C`（`\x01/\x02/\x03`）；但 ctrl+1/2/3 本身不产生命名 KeyCtrl*，实际以 `KeyRunes{'1'/'2'/'3'}`（ASCII digit 49/50/51）或 `KeyRunes{0x11/0x12/0x13}` 到达，取决于终端类型（Windows Terminal vs conhost）。
  - 原代码只匹配 `KeyRunes{0x11/0x12/0x13}`，遗漏了 `KeyRunes{'1'/'2'/'3'}` 和 `KeyCtrlA/KeyCtrlB` 形式。
  - 同时发现：`KeyCtrlC` 在 `handleNormalKey` 顶部被 quit 拦截（`if msg.Type == tea.KeyCtrlC { m.quitting = true; return m, tea.Quit }`），不能用于排序。
- **修复**：sort hotkey 匹配扩展为：
  - `KeyRunes{'1'/'2'/'3'}`（digit rune 形式，Windows Terminal 等现代终端）
  - `KeyRunes{0x11/0x12/0x13}`（控制字节形式，部分终端）
